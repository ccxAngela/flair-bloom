## 单键计时复核（2026-11-03）

本轮针对近期版本是否因连发速度变化影响物理按键与 WASD 移动进行复核，对比 `v0.8.2` 与 `v0.9.0`。版本行为变化以根目录 `CHANGELOG.md` 为准，本节保留核对依据、实验边界和本轮结论。

### 计时依据

- 关联实现提交：`0f85cd3`（统一目标队列与键盘录制）。单键规则也经过 `OutputQueue`，主行间隔与高级设置的单步间隔共用 `steps[0].interval_ms`，不存在正常连发间隔之外再重复等待一份序列间隔。
- `v0.8.2` 的 `SchedulerWorker::process_due` 在发送前安排按下／释放相位的截止时间，正常调度且通道耗时未超出相位等待时，发送耗时被原有间隔吸收。
- `v0.9.0` 的调度器把发送完成时间交给 `OutputQueue::acknowledge`，下一拍和并发节流均从完成时间起算。即使只有一个目标，实际周期也可能略微拉长；通道耗时越短，差异越小。
- 理想准时调度示例：设置 10ms 间隔，按下、释放调用各耗时 1ms，按压时长 3ms。旧版在 0ms 起拍、3ms 开始释放、10ms 下一拍；新版在 0ms 起拍、1ms 完成按下、4ms 开始释放、11ms 下一拍。这是计时起点变化，不是把两份 10ms 相加，也不是证明驱动发送本身变慢。

### 验证边界

两个版本分别构建 release 模式的 `scheduler_stress`，在 macOS 上使用不发真实按键的发送替身，设置 `--rules 1 --interval-ms 10 --duration-ms 2000`，改变 `--dispatch-cost-us`。报告为输入事件数／秒，下表除以二换算成完整点按数／秒；停止清理和系统调度抖动也会影响短时采样。

| 每事件模拟发送耗时 | 0.8.2 点按／秒 | 0.9.0 点按／秒 |
| --- | ---: | ---: |
| 0ms | 87.94 | 93.83 |
| 1ms | 90.83 | 82.97 |
| 3ms | 90.80 | 71.88 |

1ms、3ms 均为人为施加的耗时，不是实际驱动测量；对应降幅只证明该条件下的计时差异，不能作为 Windows 用户的实际降幅。无额外发送耗时的本次采样未出现降速。核心测试 `cargo test -p burst-engine -p win-input --locked` 在 macOS 上通过 145 项，不包含 Windows 专属驱动与游戏内验证。

### 本轮结论

确认单键在发送有耗时时可能轻微变慢，保留当前实现，仅补充记录。此项变化没有提高注入频率，不作为“连发过快造成输入积压、卡住物理移动”的原因；这不替代 Windows 真机对其他输入路径的排查。本轮未修改注入、调度或按键处理逻辑。
