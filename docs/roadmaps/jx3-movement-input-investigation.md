# 剑网三连发期间无法前进：输入排查

Status: investigating

Goal: 定位副本内使用游戏模式（Interception）连发时偶发无法移动的原因，分别核对奶妈与输出玩家的路径。长按 `1`、开启 `5` 切换连发是奶妈反馈中的一组操作，不能作为所有反馈的共同前提。当前没有复现现场，静态分析不能作为根因确认。

## 反馈与验证边界

- 用户反馈的现象是按 `W` 无法前进，不是松开后继续移动。截图中 `1` 为长按连发，`5` 为切换连发，`W` 未配置连发；截图表示规则配置，不足以证明其他规则当时是否运行、实际输出目标与间隔。
- 用户确认出问题的机器也使用游戏模式（Interception）。本机昨晚长时间实测没有复现；是否与反馈机器具有相同技能绑定、宏内容、间隔、设备及插件环境尚未核对。
- 反馈最严重的花间用户同样使用游戏模式，问题发生在洛阳之战；用户反馈打本卡移动键，打木桩好像不卡。这里的“卡”明确指移动键失效，不再重复询问是否为画面掉帧。“木桩好像不卡”是场景差异线索，尚不是受控对比结果。
- 已只读解密其分享的 `.qzh` 并通过认证：8 条启用规则分别为 F、E、4、5、C、X、2、3，全部是同键 Hold、单步 10ms，无分组；F1 共用全局启停，其余全局热键未绑定。没有 W/A/S/D 输出、跨规则输出触发或多步队列。文件不包含输入通道，游戏模式由用户另行确认；元信息的应用版本不能代替实际运行版本。真实配置、规则 ID 与署名不入仓。
- 另一反馈用户的恢复顺序是：松开长按连发和移动键，先按移动键，再长按连发。该反馈支持优先追查「新移动按下未建立／状态被清除」；不能由恢复顺序反推具体丢失层，也没有证据证明调换顺序是稳定修复。
- 游戏有传统和摇杆两种移动模式。用户指出传统模式 A/D 转面向，按住右键后 A/D 平移，鼠标左右键一起按也可前进；这些是常用操作，不能把右键统一当成旁路镜头操作。
- 用户明确 `5` 用于快速选中团队中血量最低的队友，来源可能是插件；`1` 应为加血技能，具体技能尚不确定。反馈环境涉及剑心、茗伊，但 `5` 对应哪个模块／注册命令尚未确定。不能继续把 `5` 当成默认技能栏第 5 格，也不能把每次 `5` 计为一次技能请求。
- 用户强调异常是偶发。排查以时序、状态切换和恢复边界为重点；一个功能固定存在、某个分支能禁止移动，不足以解释为什么相同操作通常正常。
- 当前范围只看副本环境，本外流程不继续调查。输出玩家也有反馈，不能用奶妈的最低血量选人插件路径解释全部案例。
- 用户补充多在躲 BOSS 技能时发现卡脚，也可能站桩时已经失去移动响应、只是没有移动需求而未发现。必须区分发现时机和触发时机；不能据此认定由 BOSS 施法、转阶段或刚收到控制效果触发。
- 本机另有可观察现象：C 绑定角色面板，长按连发导致面板反复开关后退回角色选择界面。尚无该次退出的对应客户端日志或服务器原因码。
- 本机无法复现、反馈用户难以准确描述操作且难以配合实验，是当前排查约束。后续不能把用户执行测试矩阵、切绑定或等待再次异常作为推进工作的前提。
- 本轮读取本地游戏文件、配置和相关日志，静态分析磁盘上的 PE 与 Lua 字节码；资源包通过独立读取器调用游戏文件系统 DLL 读取，没有执行 Lua。没有启动游戏、注入测试按键、读取游戏进程内存、修改游戏或助手运行配置。
- 排查日期为 2026-11-08，源码基线为 `527ed65`。没有据推测修改输入逻辑。

## 静态输入路径

以下位置均为文件内 RVA，不是运行时绝对地址。方法名来自程序自身日志字符串，其余结构字段含义由指令推断。

| 观察 | `KGUICocosX64.dll` | `KGUIX64.dll` | 能说明什么 |
| --- | --- | --- | --- |
| 热键消息处理 | `0x12d080` | `0x0d7420` | 区分 `WM_KEYDOWN/UP`、`WM_SYSKEYDOWN/UP`，处理按键的首次按下与重复按下 |
| 检查消息 `lParam` 的 bit 30 | `0x12d136`、`0x12d18c`、`0x12d3c8` | `0x0d74d6`、`0x0d752c`、`0x0d7768` | 部分重复 down 不走首次按下的处理路径；不是每个 down 都重新启动热键 |
| 按键释放处理 | `0x12cb50` | `0x0d6f00` | 普通键按键码匹配按住列表；释放目标命令并移除对应记录 |
| `RefreshKeyDownData` | `0x12c950` | `0x0d6d30` | 从已登记命令的按住标志重建列表，不是直接轮询所有物理键 |
| `FlipAllDownHotkey` | `0x12d650` | `0x0d79f0` | 清空热键按住列表、清除相关命令标志，并调用释放路径 |
| 应用／非客户区停用时集中释放 | `0x131d7f`、`0x131d18` | `0x0dc14f`、`0x0dc0e8` | `WM_ACTIVATEAPP(0x1c)` 或 `WM_NCACTIVATE(0x86)` 的停用分支会集中释放 |
| Lua `IsKeyDown` 的底层查询 | `0x130bd0` | `0x0daf70` | 使用 `GetKeyState` 高位查询键与修饰键，不等同于全局实时物理状态 |

`KGUICocosX64.dll` 的窗口消息分发表将 `0x1c` 映射至 `0x131d63`、`0x86` 映射至 `0x131d01`；两者在 `wParam=0` 时进入上表的集中释放调用。

Windows 对 bit 30 的定义是消息生成前该键是否已经按下，可以区分首次 down 与自动重复。[WM_KEYDOWN 文档](https://learn.microsoft.com/en-us/windows/win32/inputdev/wm-keydown)。`GetKeyState` 随调用线程读取键盘消息而更新，不能用来代替硬件实时状态。[GetKeyState 文档](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-getkeystate)。

据此能确定：游戏至少有一条基于消息和内部按住状态的热键路径，不能仅凭帧率推断短点按必然丢失。不能据此排除其他输入路径、技能脚本或底层驱动问题。

### 与本次现象的关系

- **普通 `1/5 up` 不应直接清除 `W`。** 已看到的普通释放分支会比对键码，存在多个命令的按住记录；没有证据支持“游戏只能记住一个按键，松开数字键就把移动也松掉”的解释。管理器另有当前键／重复命令字段，但存在这些字段不等于整个游戏只支持一个按住键。
- **焦点变化值得验证，但尚无现场证据。** 集中释放会清除游戏内部按住状态。若物理键仍按着、后续输入仅为重复 down，部分路径可能不会按首次 down 重建状态。这可以解释一类需要松开重按才能恢复的现象；本次是否发生停用、是否经过这条分支，以及前进脚本如何消费命令，均未确认。
- **必须区分输入与技能行为。** 即使游戏收到 `W`，连续触发的具体技能／宏、输入框或界面仍可能影响前进。尚未取得反馈机器的技能绑定与异常当时状态，不能把这个候选方向写成游戏的确定行为。

助手当前代码的对应边界：

- `packages/burst-engine/src/lib.rs` 的 `keyboard_hook_proc` 末尾调用 `CallNextHookEx`；自身注入过滤也继续传递事件，没有依据 `handled` 返回非零吞键。内部物理事件去重不等于系统事件被拦截。
- `packages/win-input/src/interception.rs` 将各目标键分别映射为扫描码并发送一个 stroke；当前封装没有设置物理键拦截过滤或执行接收后转发循环。底层驱动行为不能单凭封装证明正常。
- 两条数字键规则不应由正常调度路径生成 `W up`。仍需核对反馈配置中是否有额外输出步骤／热键，并采集实际事件，不能用截图代替完整配置。

## 移动控制层的独立排查

`JX3RepresentX64.dll` 有独立于 UI 热键管理器的角色控制层。以下位置同样为本机文件的 RVA：

| 路径 | 位置 | 确认内容 |
| --- | --- | --- |
| `Move` 接口 | `0x8e95c0` → 跳板 `0x4999` → `0x3a89d0` | 更新角色控制器的横移、前进及另一个方向字段，并追加类型 `5` 的控制快照 |
| `GetMoveInfo` | `0x3a8850` | `pnForward` 对应控制器 `+0x50`，`pnStrafeRight` 对应 `+0x4c`，`pnRotationRight` 对应 `+0x3c` |
| 控制快照追加 | `0x3a8a70` | `+0xb8` 为暂存计数，`+0x128` 起为 64 字节快照数组；计数达到 `0x40` 时跳过追加，这个容量分支本身不记日志 |
| 暂存转移 | `0x3a8c30` | 在临界区中将暂存快照移入后续队列，随后清零暂存计数 |
| `CommitInput` | `0x3ac020` → 跳板 `0x1ba81` → `0x3a8020` | 按记录时间处理控制快照；后续队列超过 `0x200` 时记录 `[RL] Input count %d` 并清空队列 |
| `InvalidCtrlInput` | `0x3b3fd0` → 跳板 `0x5e39` → `0x3a8950` | 更新控制时间基准、清空暂存计数和后续队列 |

静态分派可以看到 8 类控制记录，`Move` 生成的是类型 `5`。这不是 Windows 原始键盘消息队列，也没有证明每次 `1/5` 技能点按都会生成控制快照。不能把每秒按键数直接与 64／512 的容量相除，推导出游戏必然积压或漏 W。

容量边界确实存在，但尚未构造出符合本次配置的可达溢出路径，也未证明方向状态在溢出后不能被恢复。它是可以继续追踪的静态边界，不是已确认缺陷。前述 UI 热键按键码分别释放的结论，只覆盖热键管理器，不能外推为角色移动链路没有问题。

助手的调度审查没有找到数字键规则直接生成 W 释放的正常路径；发送账本锁也没有由键盘钩子获取。当前没有足以支持修改输入行为的确定性代码缺陷，未添加猜测性补键或驱动切换。

## 实际热键脚本与两种移动模式

资源包内 `ui/Hotkey/bindings.ini` 把 `MOVEFORWARD` 的 down/up 绑定到 `MoveForwardStart/Stop`，数字技能栏则经过 `ActionButtonDown/Up` → `ActionBar_ButtonDown/Up`。`ui/Script/hotkeys.lua` 是带原始行号、去除调试名称的标准 Lua 5.1 字节码，以下结论来自指令分析，不是根据函数名称推测。

| 脚本入口 | 原始行号／原型 | 确认行为 |
| --- | --- | --- |
| `MoveForwardStart` | 703–719，`root/65` | 有玩家时先调用 `HoldW(1)`；普通分支先启用前进控制，再调用 `ResponseWASDKey("Forward", true, 是否双击)`；另有局部模式标志控制的技能分支 |
| `MoveForwardStop` | 721–730，`root/66` | 调用 `HoldW(0)`、处理位移／冲刺释放，最后关闭前进控制 |
| 移动模式分派局部函数 | 679–685，`root/61` | 传统模式调用 `Camera_EnableControl`，其他模式调用 `Scene_EnableFreeMoveControl` |
| `TurnLeft/RightStart` | 776–810，`root/71、73` | 位移热键响应返回已处理时，可以不启用原来的转向控制；与普通 W 先启用再响应的顺序不同 |
| `ResponseWASDKey` | 488–565，`root/46` | 按方向累计 down/up 计数、生成合成方向、调用 `ResponseDisplacementHotkey`，还有双击前进触发冲刺的分支 |
| `ActionButtonDown/Up` | 1196–1202，`root/102、103` | 转交技能栏；已检查的技能栏按下函数没有直接调用前进释放或清除移动状态 |

`HoldW` 不是 Windows 按键重发：主程序 `KCharacter::LuaHoldW`（`0x41bf10`）只把参数转换为整数写入角色 `+0x2bc`。它与镜头层的前进控制标志是两份状态，不能只凭其中一份判断 W 已建立有效移动。

`ui/Script/OperationModeBase.lua` 中：

- `CLASSICAL_MODE=0`，`JOYSTICK_MODE=1`。`GetOperationMode`（92–108，`root/0`）在角色 `nFollowType == FOLLOW_TYPE.SIMMOVE` 或 `bLockedFace` 时返回传统模式及一个额外标志；因此设置中的模式不能完整代表所有时刻的有效分支。
- `FreeMoveControl`（367–436，`root/16`）分别保存前后左右的按住布尔值，重复的同向 down 会直接返回；有效变化更新方向向量，再调用 `Camera_EnableControl` 开关前进。摇杆模式不只是把传统模式的 A/D 名称换掉。
- `ClearMoveState`（127–144，`root/2`）清方向布尔值和向量，关闭六种方向控制，调用 `HoldW(0)`。`ClearMoveStateByPlayerState`（111–125，`root/1`）在进出 SIMMOVE 跟随或锁面向状态变化时调用它。
- `FIRST_LOADING_END` 注册 `RENDER_FRAME_UPDATE` 回调；该回调在所选／覆盖模式不是传统模式时执行上述状态检查和角色转向。这里存在无需物理 W up 就主动清移动状态的路径，但没有证据证明本次反馈经过该路径。
- `PLAYER_REVERSE_MOVE` 回调会关闭前后控制，再按当前移动布尔值和 `bReverseMove` 重新启用其中一个方向。它与完全清除状态不同，不能混写成所有角色状态变化都会永久丢移动。

用户的恢复顺序更值得追查「有效移动状态什么时候建立／清除，以及是否等待新 down」。它也可能由消息、驱动或游戏状态机中的其他问题产生，不能据此确认摇杆模式或某个技能有缺陷。

## 右键、双鼠标与原生方向状态

`ui/Script/control.lua` 明确给出控制编号：前进 `0`、后退 `1`、左／右转 `2/3`、左／右平移 `4/5`、镜头 `6`、角色跟随镜头 `7`、自动跑 `10`。`JX3RepresentX64.dll` 的全局状态对象从 `+0x2e340` 开始，每种控制占 `0x20` 字节；以下偏移均相对于该全局对象。

| 原生路径 | RVA／关键位置 | 确认行为 |
| --- | --- | --- |
| `EnableControlCamera` 实际消费者 | `0x8fc410` | 更新对应方向的控制状态；启用前进或后退时，还会清自动跑状态。前面的 `KGameWorldHandler` 和事件适配器是转发层，不能当成最终消费者 |
| 开关控制状态 | `0x8fc3c0`／`0x8fc350` | 更新控制状态的低 16 位和变化标志，保存关联时间数据；不是单一「当前键」槽 |
| `UpdateCharacterCameraControl` | `0x940950`，前进计算 `0x940b21–0x940b8a` | 除前进／自动跑外，在允许鼠标移动的条件下，控制 `6` 与 `7` 同时有效也会产生前进；后退会抵消前进 |
| 同一函数中的平移计算 | `0x940c20–0x940c6a` | 控制 `7` 有效时，把左／右转控制并入对应平移；显式平移键也参与计算。这与用户描述的传统模式右键+A/D 一致 |
| 输出移动方向 | `0x940df3–0x940e60` → `0x8e95c0` → `0x3a89d0` | 依据控制锁决定是否写移动输出；普通可移动路径会提交当前方向，不是只有 Windows 首次 down 才生成控制快照 |

这几条入口在原生移动计算汇合，但 W 的脚本按住状态、镜头控制状态、双鼠标条件、摇杆方向向量分别存在。不能把「A/D 还能转镜头」等同于角色移动通道正常，也不能假设鼠标前进一定能绕过 W 的所有下游问题。本次没有反馈鼠标组合在异常时的表现，不补造该事实，也不要求用户执行对比矩阵。

`ui/Config/Default/Scene.lua` 把鼠标和摇杆的上游也接起来：

- 657–670（`root/31`）依据场景 `bLDown/bRDown` 与左右鼠标启用状态，分别开关 `CONTROL_CAMERA` 和 `CONTROL_OBJECT_STICK_CAMERA`。因此原生控制编号 `6/7` 与实际鼠标操作有脚本对应，并非只根据相邻内存偏移猜测。
- `Scene_EnableFreeMoveControl`（609–617，`root/26`）先按控制编号保存请求。前进经过 590–604（`root/25`）合并「保存的键盘前进请求」与「左右鼠标同时按下」，再调用 `FreeMoveControl`；其他方向直接转交。摇杆中键盘与双鼠标前进在这里已汇合一次。
- `OnKillFocus`（483–491，`root/21`）在场景记着鼠标按住时主动执行相应 `OnSceneLButtonUp/OnSceneRButtonUp`，无需等物理鼠标 up。鼠标释放链会重新计算控制和摇杆前进；这不是直接清除所有键盘移动的函数，不能只凭 UI 焦点变化便认定 W 必然停止。
- `Scene_SetMoveControl`（978–999，`root/66`）保存／恢复操作模式，必要时调用 `MoveForwardStart/Stop`，另进入／离开特定镜头控制。该入口的存在也不证明 `5` 调用了它。

存在两种不同的控制锁边界：

- `EnableControlCamera` 在 `0x8fc434` 检查输入锁位 `0x8`；锁定且为启用、控制编号小于 `10` 时，直接返回，不先保存本次启用。锁本身为根组件类型 `8` 的 `+0x20` 位掩码，查询／设置函数分别为 `0x91eb50`／`0x91ebb0`。
- 已找到 `EnterNpcDialog` 在 `0x939735` 设置 `0x9`，`LeaveNpcDialog` 在 `0x93a1af` 清除 `0x9`。这能证明对话期间存在上述门禁，不能外推普通技能连发会设置同一锁位。
- `UpdateObjectState`（入口 `0x943580`）设置的是另外的 `0x2/0x4` 锁位；方向计算检查组合掩码 `0x6`。这些按角色状态更新的输出限制，与「启用事件不被保存」不是同一条路径。

因此，锁定位只构成已确认的机制，不构成本次根因。特别是不能把所有锁位统称为技能限流，也不能因为摇杆重复 down 被忽略，就宣称已构造出连发必现卡键。

## 偶发边界：首次按下与临时屏蔽错位

**这是一条待验证条件链，尚不是副本内奶妈与输出玩家的共同解释。**「W 首次 down 恰好进入临时屏蔽窗口，窗口关闭后没有重新建立移动状态」能从 `KGUICocosX64.dll` 对上局部机制，但未证明副本普通施法、连发或剑心／茗伊选人会开启该窗口。「窗口」指屏蔽布尔状态持续的时间段，不是游戏里已经发现的施法冷却计时器。

| 顺序／边界 | 代码证据 | 能说明什么 |
| --- | --- | --- |
| 命令 down 先登记按住 | `0x12cdec` 写命令 `+0x2b4=1`；后续 `0x12ce5e` 起加入按住列表 | 热键管理器记住 down，不等于移动脚本已执行 |
| 屏蔽时跳过命令脚本 | `0x12ce0f` 检查命令 `+0x2b0`，非零绕过 `0x1ec140` 的命令执行；`0x131020` 仍发 `EXECUTE_BINDING`，携带屏蔽状态 | 屏蔽并非把整个消息当作从未发生；事件监听器仍有机会看到状态，不能一概称为吞掉全部事件 |
| 修改屏蔽没有重放 down | `Hotkey.ShieldAll` 的 `0x1cb4b0`、`ModifyShield` 的 `0x1cb59c` 只更新命令 `+0x2b0` | 此接口自身没有检查物理键或补执行启动移动；其他脚本另行修复的可能仍需检查 |
| 默认 W 不开启按住循环 | `LoadBinding 0x12df1d–0x12df31` 读取 `loop` 的缺省值为零；`MOVEFORWARD` 节没有该字段。`Hotkey.EnableKeyDownLoop` 在 `0x1cadbf` 可另改 `+0x2ac` | 默认绑定不能指望每次系统自动重复都重做首次 down；运行时插件是否改过仍未知 |
| 重复 down 的恢复边界 | `0x12d3a9–0x12d3cd` 结合当前命令／键及 bit 30 分派，部分 repeated down 跳过首次处理 | 暂时恢复可用之后，物理 W 仍按住不保证自动重建；需要明确检查后续实际分支 |
| 松开重按 | 普通 up 按键释放记录，下一次 down 的 bit 30 为零 | 可以重新进入启动移动路径，与反馈的恢复方式相容；不证明反馈一定命中了屏蔽窗口 |

这条条件链能容纳「先建立移动，再进入连发」与「连发期间才按移动」的差异，但缺少副本内的实际开启者，因此不再作为首要共同根因。缺口是调用关系与可达条件：谁屏蔽了移动命令、是否确有短暂窗口、插件的 `EXECUTE_BINDING` 回调是否补偿、物理重复 down 在实际配置中如何分派。它不是本机游戏复现结果。

### 屏蔽接口与实际调用者

已扫描模块清单中成功读取的 1,889 份 Lua，以及此前读取的少量独立脚本；标准字节码可递归检查到常量和原型。命中 `ShieldAll/ModifyShield/sheild_hotkey` 的本体调用者集中在特定界面／模式，已核对多组明确的开关配对，未在普通 `ActionBar`、`skill.lua`、`SkillPressCast` 中找到这些接口的直接调用。该结论不覆盖未读取的资源、动态拼接的函数访问、非标准插件代码和服务器脚本。

屏蔽 API 本身只接收调用方传入的状态，没有「每次施法自动开关」「键频超过阈值自动屏蔽」「固定若干毫秒后自行恢复」逻辑。已核对的配对中，开启与关闭由界面／模式生命周期调用；个别教学动画通过 `DelayCall` 延后关闭。根据只看副本的约束，这些本外专用流程不继续扩展，也不作为战斗卡脚解释。不能把「接口存在」写成「副本里每次技能都会产生窗口」。

必须区分以下机制：

| 机制 | 状态与入口 | 恢复边界 |
| --- | --- | --- |
| 单条／全体命令脚本屏蔽 | 命令 `+0x2b0`，`ShieldAll/ModifyShield` | 只改布尔状态；已按住记录和实际移动脚本可以不一致，接口本身不重放 down |
| 热键管理器整体启用 | 管理器 `+0x4c`；全局对象中为 `+0x63a4`，`Hotkey.Enable 0x1caa00` | 跨零／非零切换时 `0x1caaa8` 调 `FlipAllDownHotkey`，再写启用值；与单改命令屏蔽不同，不能假定先前建立的移动会被保留 |
| 原生角色控制锁 | `JX3Represent` 根组件类型 `8`、字段 `+0x20`，不同位对应不同门禁 | 有的拒绝新启用，有的在每次计算时暂时压制输出；不能把各个位合并为同一个屏蔽窗口 |
| 摇杆方向缓存清除 | `OperationModeBase.ClearMoveStateByPlayerState` → `ClearMoveState` | 状态变化可清方向缓存，不要求收到物理 W up；不是热键屏蔽 API |

全体屏蔽和单条屏蔽直接覆盖布尔值，接口中没有按调用者计数或嵌套栈；调用顺序可能影响最后状态，但目前没有副本反馈进入这类重叠开关的证据。已读本体 `EXECUTE_BINDING` 监听者主要承担教学／轻功界面反馈，不能据此认定存在普通战斗中的 W 自动补偿。

另一条分开的候选是热键上下文变化：`SearchBinding 0x130e80` 先按当前上下文查找，再回退全局；`Hotkey.SetCurContext 0x1cb2f0` 更新上下文及 hash，没有在该接口里重建物理按键状态。必须追到具体上下文绑定才能判断 W 是否被遮蔽，不能因为插件可以注册热键就直接认定它会影响 W。

## 插件选人入口的证据边界

本机有剑心 `interface/JX` 与茗伊 `interface/MY`。包元数据可读，相关候选包括剑心团队辅助／基础库、茗伊团队监控／基础库；这些模块名不能代替反馈用户的实际热键绑定。部分插件 `.lua` 文件不是标准 Lua 5.1 字节码或明文，本轮未解密、未执行，尚不能声称读过其最低血量选择回调。

原生 `RaidPanel.lua` 已检查的选人入口（850–858，`root/27`）调用 `SetTarget(TARGET.PLAYER, 成员ID)`，已检查的标准默认热键配置没有最低血量选择项；这不排除其他模块注册该功能。`Teammate.SelectTeammate` 则是按小队成员序号选择，与最低血量算法不同。不能把这些普通入口直接当作 `5` 的实现。

主程序全局 `SetTarget` 可追到 `KScriptFuncList::LuaSetTarget 0x1e8d70` → `KCharacter::SetTarget 0x34ccf0` → `0x12d8b0`，后者发送协议 `0x44`、长度 `0x10`，同样经公共发送队列。前面两层有同目标短路，因此即使插件使用它，连续按 `5` 也不等于连续发送同样数量的选人包。该角色目标路径会通知世界接口；尚未把其所有事件订阅者追完，不能由函数内未直接操作焦点外推整个插件回调不改变焦点。

## 从控制快照到发送队列

控制快照类型 `5` 在 `0x3a81a0` 的分派中更新移动字段并调用 `0x3a8d30`，后者经世界接口虚表 `+0x90` 调用主程序 `KGSO3WorldClientInterface::MoveCtrl`（`0x18a3a0`）。该接口比较角色 `+0xfc8/+0xfcc/+0xfd0/+0xfd8/+0xfd4` 的参数，只在参数变化且世界 `+0x1db68` 为零时设置 `+0x1008` 待发送标志。

主循环在 `0x16fe9e` 检查待发送标志，`0x16fea7` 先清标志，再于 `0x16fee3` 调用 `KPlayerClient::DoMoveCtrl`（`0x12a010`），构造协议 `0x7`、长度 `0x31`，转交公共 `Send`（`0x165ce0`）。该调用点没有依据返回值立即重设标志；这是一处需要结合完整同步／重试路径判断的边界，不能单独认定丢包永久不重试。

世界 `+0x1db68` 已追到 `BeginForwardCharacterPosition`（`0x188c80`）递增、`EndForwardCharacterPosition`（`0x188fb0`）递减。后者还恢复之前保存的移动控制字段。它不是已确认的普通技能输入锁，不应用字段存在本身解释此次卡键。

原生方向计算会再次调用 `Move`，所以仅发现快照队列有 64／512 的容量，仍不足以解释持续不走：还必须说明后续有效方向为何没有重新提交或到达下游。数字键点按频率、控制快照频率、实际技能请求频率、网络包发送频率不能互相替代。

### 副本战斗中的持续失效与恢复

角色逻辑更新 `0x33dcc0` 的循环在 `0x33ddc8` 调用 `KPlayer::MoveCtrl 0x3a3b30`。控制快照类型 `5` 则在 `JX3Represent 0x3a83ff` 调用 `0x3a8d30`，后者重新计算并在 `0x3a8e7a` 调用世界移动接口；这一层没有只允许首次方向变化进入的比较分支。由此不能把「某次角色状态门禁拒绝移动」直接解释为持续失效：还要说明后续逻辑更新／方向快照为何不能恢复。

目前需要分别检查：

- **按键状态未建立**：系统事件到热键脚本、场景／摇杆缓存的哪一层缺少有效前进状态。站桩期间没有移动需求，不能判断这份状态何时开始异常。
- **已建立的状态被清除**：摇杆分支已找到不依赖奶妈选人的清除入口，但不能外推所有职业、两种移动模式和所有技能都经过它。
- **输出持续被压制／同步覆盖**：检查角色控制锁、客户端预测与服务器调整，区分短暂的正常控制与解除后仍未恢复。重按可恢复并不独立证明物理事件丢失。

对摇杆候选的进一步定位：主程序属性表将 `nFollowType` 映射到角色 `+0x150`（getter `0x454530`），`bLockedFace` 映射到 `+0x391`（getter `0x454950`）。枚举描述表 `0xa723a0` 给出 `LOCKED_FACE=0x13c`；处理表以 `0xafaef0` 为基址，初始化 `0x3e529a–0x3e52a1` 将该槽写为 `0x3e9950`。该处理函数按应用／撤销参数写锁面向字节，说明这是角色属性处理的一部分，不能因名字带「锁」就当成热键屏蔽。

`ClearMoveStateByPlayerState` 在上述状态变化时清缓存，但尚未证明具体副本技能／效果会触发对应变化，也未证明其后没有其他入口重建方向。仅摇杆分支的条件链不能用于解释已确认使用传统模式的案例；反馈机器的具体移动模式目前尚未确定。

同步层另有独立边界：`KGSO3WorldClientInterface::MoveCtrl` 在角色 `+0xfc4` 非零时返回；该字段可由 `OnAdjustPlayerMove` 的 `0x134cff/0x134f1b/0x134f58` 更新，来源包含服务器调整包的状态位。它不是前述 UI 屏蔽标志。后续应核对调整后的持续更新／恢复路径，而不是只看到一个返回条件就判定为副本卡脚根因。

`HoldW` 的已见原生读取位于角色处理函数 `0x3476a0` 的 `0x34797a/0x3479e0/0x347ae5`，周围涉及地形、腾空、跑酷／移动状态及 `DoCharacterMove` 请求条件；这不足以把 `HoldW` 解释为通用的施法解锁开关。不能仅凭「先 W 后技能能恢复」推断所有读条都有一个专用 W 屏蔽窗口。

## C 连发退出：实际请求与客户端断线机制

这条线索具有排查价值：角色面板开关并非纯本地绘制。它目前不能与 W 无法前进合并为一个已确认原因。

| 路径 | 位置 | 确认内容 |
| --- | --- | --- |
| C 默认热键 | `TOGGLE_EQUIP_PANEL` | down 执行 `TogglePanel("EQUIP")` |
| 角色面板打开 | `ui/Config/Default/CharacterPanel.lua`，4040–4119，`root/156` | `Open` 末尾无条件调用 `RemoteCallToServer("OnSyncEquipIDArray")`；另外的称号／铭刻请求有首次展示或缓存条件，不能混为所有请求均每次发送 |
| Lua RPC 包装 | 主程序 `0x1e72e0` → `0x24f070` | `KScriptClient::Call` 序列化参数，`0x24f15b` 调用 `DoRemoteLuaCall`（`0x12c0f0`） |
| RPC、技能与移动共用发送入口 | `DoRemoteLuaCall 0x12c0f0`、`DoCharacterSkill 0x124a10`、`DoMoveCtrl 0x12a010` | 分别构造协议 `0xb8`、`0x1b`、`0x7`，都交给 `Send 0x165ce0`；不等于每次连发均成功产生技能包 |
| 发送队列容量 | 初始化 `0x1332bd–0x1332c9` | 为 `this+0x19580` 初始化 `0x400` 个元素 |
| 队列入队失败 | `0x165d92–0x165daf` | 记录 `Client send pack list full!`，设置 `this+0xeb70=1`、`this+0xeb74=0` |
| 主动断线 | `CheckReconnect 0x11c230`，关键 `0x11c2e4`、`0x11c32a` | 发现该标志后调用 `Disconnect 0x11d810`；后者记录 `[KPlayerClient] GS disconnected. bWaitReconnect = %s.` |

网络线程 `0x166000` 也检查 `+0xeb70`。每轮发送处理最多取 32 包，还执行接收和其他处理；循环含 10 ms 等待。这里不能简单换算硬吞吐上限，更不能仅凭 C 连发频率证明队列会满。另有 `Unconfirm send buffer full!` 未确认发送缓存保护，未证明本机这次命中。

因此，**C 连发退选角不必然意味着服务器接口限流**：客户端自身存在发送队列溢出后主动断线的完整路径；也仍可能有服务器断线或其他原因。没有该次 `Client send pack list full!`／断线日志，不能宣布触发了本地保护。发送队列满会进入断线流程，也使它不能直接解释「仅移动失效，松键重按恢复而不重连」的反馈。

排查中排除的错误线索：`SEND_COUNT_LIMIT/RECV_COUNT_LIMIT` 位于赠礼／代付枚举，`RATELIMITING/TOOFAST` 来自 HTTP／libcurl 依赖；它们不是剑三键盘或技能限流证据。账号踢出原因枚举也不能代替 GS 连接断开的全部原因。

### 本仓长时间激活的边界

- `OutputQueue` 的步骤索引到末步归零，循环数是饱和相加的 `u64`；下一次截止时间从本次发送完成时间起计，不按“启动时间＋累计拍数×周期”计算。Windows 等待使用 `Instant` 差值和负的相对 100ns 计时，转换前钳制范围，不依赖 32 位累计毫秒值。连续连发本身不会增加停止代际或运行 ID。
- 正常 Hold 首次按下只发送一次 Start，自动重复由物理按住集合去重。后续点按直接在 worker 内推进，不逐拍追加控制命令；规则、进度、目标所有者与模拟按下账本按当前规则／按键覆盖和删除。持续运行不是事件历史表。
- Interception 的回灌识别使用每个 stroke 的 `information=SIM_MARKER`；不是依赖 DD 的 50ms FIFO 名额。WebView 中继另有 200ms 时间窗，登记时清掉同键同方向过期项。固定配置与受限注入速率下，没有发现随运行小时数持续增长的路径。
- 仍有不同于“计数溢出”的边界：控制命令通道无界，极端启停／滚轮洪泛可能积压；Interception 的同步发送若阻塞，会拖住同一调度线程上的其他输出。干跑压力工具的耗时样本 `Vec` 随采样增长，但生产调度器不启用该统计。这些边界不能仅凭代码存在认定为本次物理移动键失效的原因。

`scheduler/endurance_tests.rs` 使用实际 8 个键、10ms 配置，替身只保存固定集合的计数和按住态。新增常规回归验证单键／8 键持续运行、集合长度与容量有界、配置外按键不得输出、重复按下／漏释放直接失败，以及约 25 天、50 天和一年后的迟到不追赶补发；`output_queue.rs` 覆盖循环计数饱和后继续按下与释放。

单键和 8 键分别执行八小时虚拟调度，共验证 `5,760,009` 次完整点按，停止时均处于新一拍按下期间，StopAll ACK、按下／释放配平与账本清空通过。优化构建的首次逐拍运行耗时 4.59 秒。虚拟时钟验证的是调度逻辑，不覆盖八小时真实线程调度、Windows 输入管线、驱动阻塞或游戏接收，不用于宣称游戏内不卡键。
